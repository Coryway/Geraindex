# skill 00 · 月度维护入口（先读这一份）

> **这个 skill 不生产任何数据。** 它只做三件事：让你读完该读的 → 确认环境没坏 → 判断走哪条线、调哪个 skill。
>
> 维护一旦开始，真正动手的是 01–14。00 是总台；**13 是数据闸门（能不能发）、14 是发布动作（发出去）**。

## 为什么要单独有 00

项目有 14 个 skill、6 份必读文档、一整套口径。以前每次维护都是"想起哪个跑哪个"，结果反复踩同一批坑（见文末《历史踩坑速查》）。

00 的作用是把顺序固定下来：**先读 → 再查环境 → 再判断 → 再分派**。

| 层 | 谁负责 | 管什么 |
|---|---|---|
| **导航层** | **00（本文件）** | 读什么、判哪条线、调谁、什么时候停 |
| 执行层 | `_过目/02_月度更新操作手册.md` | 每步的具体命令、验收线、回滚 |
| 参数层 | `_过目/01_封盘基准与参数冻结.md` | 基准值、公式、哪些参数不许动 |
| 口径层 | `_过目/00_全景流程图与数据字典（常驻）.md` | 字段定义、一手价口径 |

**00 和 02 不重复**：00 说"该做哪条线"，02 说"这条线怎么做"。

## 第 2 步 · 判断走哪条线（决策树，1 分钟）

```
这次维护，什么变了？
│
├─ 只有价格变了（没新型号）
│   └─► A 线：存量刷新        §2 in 02    skill 01 → 02 → 04 → 07
│
├─ 有新琴要入榜
│   └─► B 线：新增款全流程    §3 in 02    skill 08 → 09 → 11 → 12 → 05/06 → 01/02/04 → 07
│
├─ 到季度了 / 评论出事了（下架、集中故障、换代）
│   └─► C 线：评论可靠性 L    §4 in 02    skill 05/06 → 07 --apply-l → 09 扫描
│
├─ 官方改配置了 / 判读口径要重评
│   └─► D 线：静态层          §5 in 02    skill 08 → 09 → 11 → 12 → 07
│
└─ 只是录错了某个值
    └─► 单点修正：改完直接跳合流（§6 in 02），不走完整线
```

**两条以上同时要跑**：顺序固定为 **B（新增）→ A（价格）→ C（评论）→ D（静态）**。
理由：B 会产生新行，A 要给新行补价格；C/D 改分会动全榜，最后跑才不用重算两遍。

**不管走哪条线，最后都必须过合流四步**（见第 4 步）。

## 红线（违反了就不用往下做了）

1. **主榜只有 skill 07 能写**。其它 skill 一律只读或写影子。
2. **`--apply` 前必须 L1 全绿**；`_过目/01_封盘基准与参数冻结.md` 里的基准参数（b、权重、手感系数、`maxO`）月度**不许动**。
3. **判读必须用盲判包**，必须带锚点同批判。不许看价格 / 品牌 / 排名。
4. **缺失不编造**：显示「—」，不填均值、不填同类推定（除非明确标 `inferred`）。
5. **改分必须留痕**，changelog 写清哪款从多少到多少、为什么。
6. **不许为了某个排名去调 L / 调 k / 改判读**。这三个都是"改尺"，不是"修数据"。
7. **报告只写 `<项目根>/_过目/`**（数据侧）。前端侧在 `_过目`，别混。
8. 采错的产物移到 `_bak_code_<日期>/`，**不许留在 `原始数据/mb/`**（会进统计）。

## 历史踩坑速查（这些错都真发生过，读一遍能省几小时）

| 坑 | 症状 | 根因 | 怎么避免 |
|---|---|---|---|
| **代理假断网** | 所有站点全 000，看着像没网 | 系统代理指向未运行的 127.0.0.1:7890 | 先 `--noproxy '*'` 对照一次再下结论；`preflight` 会报代理状态 |
| **判"缺 4 款"** | 主榜 key 在采集文件里找不到 | 采集侧用别名 key（`Squier\|Classic Vibe` ≠ `Squier\|CV Strat`） | 先读 `05_bili_l/reconcile.py` 的 `KEY_ALIAS` / `MERGE_MAP` |
| **抓进无关视频** | 搜吉他抓到电竞视频（6 万条评论） | B站搜索页改版，标题读错元素 + 顶部热搜条目逃过筛选 | 采集后必抽查标题；`_bili_comments_20261102.py` 已修 |
| **k 档方向反了** | 「价格优先」反而选出最贵的 | k 越大越罚贵琴，标签按"小中大"贴反了 | 改 k 先跑一遍 Top10 均价，看方向对不对 |
| **disc 折扣丢失** | 45 款估算价琴 O 高估 5.26% | 用 `o_applied/o_raw` 反推 disc，而这两字段是遗留值 | 读 `p_proxy_discount`，别反推 |
| **插补假断崖** | 20.32mm 得 80 分，20.60mm 得 34 分 | 百分位归一化把 0.28mm 放大成 46 分 | 手感一律用物理量，不用百分位 |
| **轴方向定反** | 厚颈=好手感、费劲=好推弦 | 注释写"数值大=高端" | 判读前先跑 `build_feel_profile.py` 的 G3 锚点方向检验（8 组） |
| **bat 乱码** | `'dge.exe"' 不是内部或外部命令` | bat 按 UTF-8 存，cmd 按 GBK 读，中文乱码把命令行切碎 | bat 只用纯英文 + 纯英文路径（已建 `<浏览器用户数据目录>` 联接） |
| **data.js 版本漂移** | 前端进度条画偏 8% | 导出靠临时命令，`meta.maxO` 停在旧值 | 必须用 `抓取脚本/export_datajs.js`，不许手改 |
| **报告写错目录** | 252–275 写进了前端侧 `_过目` | 按 cwd 就近创建，没查数据侧已有目录 | 数据侧报告只写 `<项目根>/_过目/` |
| **净亏损取错字段** | 前端兜底算 O 时用了 `price.netCostCNY` | 该字段是旧口径残留（未封顶款用 rawPct、封顶款用 capped），66 款与 `value.v_net` 不等，最大差 1,062 元 | `FIELD_MAP.netCost` 首项必须是 `value.v_net`；`verify_all §J` 已静态断言 |
| **两套交付包** | 同一时刻存在 v5.36 与 v5.39 两个 `data.js`，都能双击打开 | 升级时新建目录但没清旧的 | 交付包只允许 `前端交付包/` 一份；`preflight` 检遗留目录 |
| **把设计后果当 bug** | 用户报「日芬总第一/Sonic 上不去」，看着像公式错 | 实为净成本口径（V=P×(1−R)）+ M^1.4 放大的必然结果，数值 100% 自洽 | 用户报反常时先做**定量归因**（算临界值、扫参数），再决定改不改公式；见 `归档/276` |
